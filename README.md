# BankStatement
Classifies bank transactions into categories with a fastText model trained on your own categorized history.

## Setup
Ubuntu (needs `sudo apt install python3-venv build-essential` to build fastText):
```
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp config.example.json config.json   # then adjust account names and transfer categories
```
Windows:
```
py -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy config.example.json config.json
```

## Usage
Every script has a `.sh` (Ubuntu) and a `.bat` (Windows) launcher that uses the `.venv`.

- `train` trains the model on all categorized transactions of the history file (`all_statements.xlsx`)
  and reports the accuracy, weak and rare categories. `train demo/all_statements.xlsx` trains on the demo data,
  `train --autotune 60` searches better parameters for 60 seconds.
- `import` reads all bank exports in `/input`, adds transactions that are not yet in the history,
  classifies them (and history entries still missing a category) and writes them to `new_import.xlsx`.
  A timestamped backup of the history is written before it is updated.
- `repair_history` checks the history against the exports in `/input` and writes `all_statements_repaired.xlsx`
  with a "Repair log" sheet (added missing transactions, removed double imports, rows moved to a legacy account,
  flagged suspicious rows). The history itself is not modified.
- `audit_categories` writes `category_audit.xlsx` with transactions whose category looks inconsistent
  (household rules, identical texts with different categories, confident model disagreement, and all transactions of
  categories given with `--categories`), each with a suggestion. Fill the `decision` column (`x` = take the suggestion,
  a category name = use that one, empty = keep) and the `to` column of the Renames sheet.
- `apply_review` applies these decisions to the history (by row id, with a backup first).

## Classification
1. Lookup: a transaction whose text, counterparty IBAN or counterparty name always had the same category in the
   history gets that category, so recurring recipients are recognized even in rarely used categories.
2. Model: all other transactions are classified by the fastText model.
3. Household rules (`household` in config.json): in the household account the real purpose is booked and incoming
   contributions are the contribution category; cash is only used for cash withdrawals. In the members' own accounts
   transfers to the household account are contributions and reimbursements from it are cash, so they cancel out the
   cash paid for the household.

The `source` column of the history shows how a category was set (lookup, model, rule, review).

Supported exports (recognized by content): Sparkasse (George json), DKB Girokonto (old and new csv format),
DKB Kreditkarte, card complete. Overlapping exports can be placed in `/input` together. Transactions are matched by
account, date and amount, so repeated identical transactions are kept and changed export texts do not cause
duplicates. Empty exports count as periods without transactions.

## Configuration
`config.json` (not versioned, defaults in `config.example.json`):
- `accounts`: account names used for each bank format, must match the names in your history
- `legacy_accounts`: where `repair_history` moves history rows that are not part of an account's exports
  (e.g. a closed account that was imported under the same name)
- `transfer_categories`: categories of transfers between your own accounts, marked in the `transfer` column
  so they can be excluded from income and spending
- `household`: household account, its IBANs, the members' last names, contribution keywords and the
  contribution and cash categories used by the household rules

## Demo
`demo/all_statements.xlsx` contains fully synthetic, randomized transactions (generated by `demo/make_demo.py`).
Your own statements, input files and trained models are gitignored and stay local.
